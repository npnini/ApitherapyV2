# Points Forklift — Design Decisions & History

Reference material only. Not needed to execute the implementation — see `implementation-plan.md` in this same folder for that. This document exists for anyone who wants to understand *why* the implementation plan is shaped the way it is.

This started as a read-only evaluation cross-checking the PDF (`Points forklift.pdf`) and `point_side_analysis` data (initially pasted as CSV text, later confirmed against the authoritative `production_point_side_analysis_2026-08-13.xlsx` workbook — that xlsx, not CSV, is the current source of truth) against the codebase, and grew into a full implementation plan over one extended planning session. Along the way, several real data corrections were also made directly in production/staging: point deletions (`GV14`, `GV4 (TW4)`), protocol/treatment repoints, coordinate fixes (`CV21`/`CV22`/`CV23`, `BL17`, `TW15`), and code/label corrections (`NH5`→`HN5`, `DU20`→`GV20`, `SI18`).

## Codebase grounding (confirmed via exploration)

- Points live in Firestore collection **`cfg_acupuncture_points`**, typed as `StingPoint` in `src/types/apipuncture.ts`. Current shape: `id, code, label{}, description{}, longText?, sensitivity?, imageURL?, positions:{corpo?:{x,y,z,isManual?}}, documentUrl?, status, reference_count`. **There is no `meridian_prefix`, `corpo_side`, or `Point_Grouping` field today** — the spreadsheet's flat columns are a derived export, not the real schema.
  - **Schema change scope, confirmed**: the **only** new field being added to `cfg_acupuncture_points` is `Point_Grouping`. `corpo_x` and `meridian_prefix` are **not** new stored fields — `corpo_x` was always shorthand for the existing nested `positions.corpo.x`, whose *value* gets modified per the established rules (Paired→Right, Midline→0, Unilateral→as-marked), not a new field being created; `meridian_prefix` stays exactly what it is today — a value computed on the fly by `pointSideAnalysis.ts` from `code`, never written to Firestore. Same for `corpo_side` — remains computed-only from `positions.corpo.x`'s sign, never stored.
- The CSV/PDF's "side/laterality" vocabulary comes from a **read-only diagnostic tool** shipped in the last two commits: `src/utils/pointSideAnalysis.ts` + `src/components/PointSideAnalysis.tsx` ("Point Side & Pairing Verification", Sidebar → Configuration). It derives `meridian_prefix` from `code` via regex, and `corpo_side` from the sign of `positions.corpo.x` (`EPS_CORPO = 0.15`, **+X = Left**). It never writes to Firestore and has a hand-curated `CODE_OVERRIDES` table for edge cases (HN1, LE6, dual-named codes, etc.) — this is almost certainly where the CSV came from.
- Point marking today (`src/components/PointPlacementScene.tsx` → `PointsAdmin.tsx`): click handler stores raw x/y/z with **zero side logic** — no forcing bilateral-left, no rejecting X=0 for bilateral, no rejecting X≠0 for midline. All of that is net-new.
- Sidebar/App routing is manual (`Sidebar.tsx` hardcoded button list + `App.tsx` `View` union + handler + conditional render, no router) — adding a "Point Grouping" item before "Points Configuration" is a small, well-understood change.
- Best CRUD template for the new Point Grouping screen: `src/components/MeasureAdmin/MeasureAdmin.tsx` (+ `measureService.ts`) — list + modal form, `addDoc`/`updateDoc` with `serverTimestamp()`, `logAction()` audit, delete blocked while `reference_count > 0`. `ProblemAdmin/` is a more decomposed multi-file variant of the same pattern.
- Treatment execution today (`TreatmentExecution.tsx`, `src/types/treatmentSession.ts`, `src/utils/pointSide.ts`): `stungPointIds: string[]` + `stungPointSides?: Record<pointId,'L'|'R'>`. This is a **single side flag per point**, not a count — there is no existing notion of "stung twice." The new L/R/S numeric-counter model is a real data-model change, not just a UI relabel, and touches `TreatmentExecution.tsx`, `treatmentSession.ts`, `patient.ts` (save), `TreatmentHistory.tsx` (tabular + list views), `PointsModelViewer.tsx`, and `pointSide.ts`'s `formatPointCode`/`getSideLabel` helpers.
- A related, informal convention already exists: `src/utils/findNearestPoints.ts` checks both `x` and `-x` when matching a click to a stored point — i.e. the app already half-assumes "only one side is stored, the other is mirrored," but it's undocumented and not enforced anywhere at write time.
- Migration script templates: `scripts/clean-translations-pii.js` (dry-run + `--project=staging|prod|emulator` selector — the only script with this scaffolding) and `scripts/fix_treatment_ids.cjs` (batched writes over `treatments`, commits every 400 ops). Combining both patterns is the right template for the three data migrations this plan requires.

## Comments (non-blocking, worth noting)

- `Point_Grouping` as stored on `cfg_acupuncture_points` should be a **document ID reference** per the PDF, so the migration script needs a code→docID lookup step, not a direct copy from the spreadsheet's code column.
- The `PointSideAnalysis` tool's `CODE_OVERRIDES`/`PREFIX_PAIRING` tables (`src/utils/pointSideAnalysis.ts`) were a ready-made source of truth for pairing edge cases while `Point_Group` didn't exist yet. **RESOLVED**: now superseded — see Phase 6 in the implementation plan, which retires `meridian_prefix`/`PREFIX_PAIRING` in favor of reading `Point_Group` directly.
- `stungPointIds`/`stungPointSides` retain-vs-delete after migration — **RESOLVED**, see "Decisions from user" below (delete after verification, per the backup/rollback procedure's deletion step).

## Decisions from user (this session)

- **Migration safety**: all three migration scripts must default to dry-run and require a clean staging-project run before ever touching prod (follow `scripts/clean-translations-pii.js`'s `--project=staging|prod|emulator` + dry-run pattern).
- **Bad legacy rows**: do not auto-correct. Produce a punch list (BL17 at x=0 tagged bilateral, TW15 at (0,0,0), HN1/Sishencong `Point_Grouping = #N/A`, and any other rows the dry-run flags as unsafe to auto-migrate) for the admin to fix by hand in Point Configuration before the real migration runs.
- **Front/back + unilateral**: superseded by the camera-lock design and revised left/right convention below (see "Front/back detection" and "Left/right (corpo_x) storage convention" sections) — front/back is no longer inferred from `corpo_z` sign at all, it's enforced by locking the camera to a canonical pose. Unilateral points remain unrestricted at marking time (reconfirmed later after evaluating and rejecting a proposed forced-side rule).
- **Legacy treatment fields**: `stungPointIds`/`stungPointSides` are deleted from each treatment document once its migration to the Left/Right/Single counter structure succeeds — no dual-write/back-compat period.
- **Env rollout**: the migration script will be run once per environment (dev, staging, production). The source spreadsheet (`production_point_side_analysis_2026-08-13.xlsx`) reflects production data — the same spreadsheet-derived PointGrouping assignments and corpo_x corrections will be used to migrate dev and staging as well, not just prod. Note: dev/staging `cfg_acupuncture_points` docs share IDs/codes with prod but may have diverged in point count or coordinates since being seeded — worth a quick diff/count check per env before trusting the prod-derived spreadsheet mapping there.
- **Per-env procedure confirmed**: for each of dev, staging, production — run dry-run, review findings, fix what's needed (manual corrections per the punch list below), then run the real update. Repeat independently per environment rather than promoting a single validated dataset.
- **Field mapping confirmed**: `meridian_prefix` column is ignored entirely for grouping purposes — only the `Point_Grouping` column (per-point, already resolved for HN-prefix splits etc.) is used to assign `cfg_acupuncture_points.Point_Grouping`. The CSV's `corpo_x` column maps to the real Firestore field `cfg_acupuncture_points.positions.corpo.x` — that is the field the migration script checks and updates (not a flat `corpo_x`).

## Midline consistency check (CV / GV / HN-midline-front, from the supplied CSV)

Requested check: are points within each midline sub-group (front vs. back) consistently on the same "side" geometrically? Using `Point_Grouping` and `corpo_z` as the front/back axis (per the earlier Z-sign decision):

- **GV group** (`Point_Grouping = GV`, expected "Midline-back"): 5 of 6 rows are consistently negative `corpo_z` (‑9.2 to ‑11.1). The 6th, code `GV14`/`Dazhui` (doc `QlA7pY0RVclmElv0uDiI`), is `x=0, y=0, z=0` — looks like an unplaced placeholder, not real geometry. There's also a **second, separate row** for the same clinical point under code `DU14`/`Dazhui` (doc `mUUROH6wPWK7hinpOCFk`) with real (negative-z) coordinates — i.e. `GV14` and `DU14` look like duplicate entries for the same point, one populated and one blank. **Gap: add `GV14` to the manual-fix punch list alongside BL17/TW15/HN1, and resolve the GV14/DU14 duplication before migrating.**
- **CV group** (`Point_Grouping = CV`, expected "Midline-front"): 20 of 23 rows have positive `corpo_z` (consistent). **3 are negative**, breaking the pattern: `CV21`/Xuanji (z=‑0.9), `CV22`/Tiantu (z=‑2.1), `CV23`/Lianquan (z=‑0.2) — all three are the uppermost neck/throat points, right at the torso-to-head transition.
- **HN-midline-front group** (`Point_Grouping = HN-midline-front`): only one point, `HN3`/Yintang, and its `corpo_z = ‑9.98` — **negative**, matching the "back" (GV) sign convention, not the "front" (CV) one it's grouped under. It's also not on the exact midline (`x=‑2.52`, already flagged separately as a geometry mismatch).
- No `HN-midline-back` rows exist yet in this dataset (the PDF's seed table anticipates one, presumably for the back sub-point of the composite HN1/Sishencong once it's split out).

**Net finding: `corpo_z` sign is a consistent front/back discriminator for standard torso points (CV vs. GV) but breaks down right at the neck/head boundary** — the same 3 CV outliers and the sole HN-midline-front point all sit in that transition zone and read as "back" by Z-sign even though CV21/22/23 are unambiguously front-of-body points and HN3 (between the eyebrows) is unambiguously the front of the face. This was a direct risk to a Z-sign-only front/back validation rule — **superseded below by a camera-orientation-based approach**, which doesn't have this failure mode.

### Front/back detection — revised approach (camera orientation, not Z-sign)

User's proposal: since the admin visibly sees which side of the model the camera is facing while placing a point (`PointPlacementScene.tsx`'s `OrbitControls`, front-facing by default per the "3D Body Model Lighting" viewer), the app can use **that orientation**, captured at click-time, as the front/back signal — instead of inferring it after the fact from the resulting coordinate's Z-sign.

Confirmed against the actual code (`src/components/PointPlacementScene.tsx`):
- `onModelClick` (~line 112) currently reads only `e.point` (the raycast's world-space hit) — no camera/orientation data is captured at all today.
- `OrbitControls` (~line 152) has no `ref` — nothing reads its angle. Three.js's `OrbitControls.getAzimuthalAngle()` gives exactly the camera's horizontal angle around the model target; adding a ref is a small, well-supported change, not a redesign.
- **Nuance to handle**: auto-rotate defaults to **on** when the Edit Point modal opens (`isRolling` initial state `true`, `PointsAdmin.tsx:506`, `autoRotateSpeed=2`) and only stops if the admin manually toggles it off. So "the initial camera pose is front" is not reliable at click-time — the model may already be mid-spin. The robust version isn't "trust the initial pose," it's **read the live azimuth at the exact moment of the click** via the OrbitControls ref — this requires no UX change and works whether or not auto-rotate was toggled off.

**Recommended design (superseded again, better idea from user):** rather than detecting camera orientation reactively at click-time, **proactively rotate the camera to the required front/back pose and lock rotation** before the admin can click at all — prevention instead of detection. Since `Point_Grouping` (and thus the required laterality) is known before a position is marked, this is straightforward:

- **Lock scope (confirmed)**: both `autoRotate` and manual/`enableRotate` are locked; `enablePan`/`enableZoom` stay on so the admin can still get precise placement from the fixed angle. Currently `enableRotate={true}` unconditionally in `PointPlacementScene.tsx:154` — needs to become conditional on the point's `Point_Grouping` laterality.
- **Canonical front/back poses (confirmed, not an open question — derived from existing code/data):** `CorpoModel` (`src/components/shared/ModelComponents.tsx:91-167`) applies no rotation to the loaded GLTF, only a centering translation — "front" is simply the model's authored orientation, which happens to line up with both viewers' default `+Z` camera position (`PointPlacementScene.tsx:150`: `[0,1.2,3]`; `BodyModelTuner.tsx:157`: `[0,0.9,5.2]`). So:
  - Front: `position=[0, 1.2, 3], target=[0, 1, 0]` (already `PointPlacementScene`'s current default)
  - Back: `position=[0, 1.2, -3], target=[0, 1, 0]` (Z-negated mirror — a 180° azimuth flip around the same target)
  - Cross-checked against real data: the midline consistency check above found `CV` (front) points cluster at positive `corpo_z` and `GV` (back) points at negative `corpo_z` — consistent with front = `+Z`, confirming this isn't guesswork.
- Lock triggers the moment `Point_Grouping` is known: immediately on open when editing an existing point; the instant a `*-midline-front`/`*-midline-back` group is selected when creating/editing a new point (re-snap if the group selection changes).
- Bilateral/unilateral groups are unaffected — they keep free rotation, since their constraint is left/right (force-left storage, reject X=0), not front/back.
- This **supersedes the PDF's "front/back negated → error message" rule** for midline groups — with rotation locked, the wrong side is physically unclickable, so the message is no longer the primary defense (may still be worth keeping as an explanatory fallback).

Z-sign remains relevant only for **auditing already-stored legacy points**, which have no orientation metadata and can only be checked after the fact from their coordinates.

### Left/right (corpo_x) storage convention — REVISED (supersedes earlier "always store Left" decision)

User's updated rule, evaluated against the established code convention (`pointSideAnalysis.ts`: `x > 0` = character's Left, `x < 0` = character's Right) and against real data:

- **Paired (bilateral) → always store on the RIGHT side of the body** (i.e. **negative** `corpo_x`), so that when the model faces the viewer, the point appears on the viewer's left — a correct, internally-consistent mirroring statement. **This reverses the earlier "force Left" decision.** Marking-time enforcement mechanism is unchanged in shape (user can click either side; the app always normalizes and saves as Right regardless of which side was clicked) — only the target side flipped.
  - Verified against real data: `SI2` (the duplicate resolved earlier this session) already complies — surviving doc `021Nr6bIpNaJFSqoU2pp` is at `x=-22.298` (Right). No rework needed there specifically, but the bulk of ~226 Paired points needed the sign-flip applied via the fresh spreadsheet re-export + write-back (roughly half currently sit at positive/Left and need flipping).
- **Midline → unchanged, `corpo_x = 0`.** UX refinement: instead of a hard-block error when the user can't mark exactly on center, the app should **ask** whether to correct the marking to midline (softer than the PDF's original error-message-only approach).
- **Unilateral → UNRESTRICTED, no forced side.** Evaluated and rejected a proposed "always store Left" rule for this group: unlike Paired (a genuinely symmetric structure where the canonical storage side is an arbitrary choice), "Unilateral" means a specific, non-mirrorable side that can differ point-to-point. Checked against real data — `LE6`/Dannangxue is currently the *only* Unilateral-group point, clinically defined on the **right leg specifically** (gallbladder is a right-sided organ, per the point's own reference note), correctly stored at `x=-15.30` (Right) today. Forcing all Unilateral points to one fixed side would have broken this. **Decision: leave as-is — point coordinates are stored exactly as the user marks them, no forced normalization, no modification to `LE6`.**

### 3-environment rollout procedure (user's plan, evaluated — sound)

1. User regenerated a fresh spreadsheet export from current production state, then hand-corrected `Point_Group` assignments and `corpo_x` so that every Paired point reflects the revised Right-side convention above.
2. **Production**: write all corrected coordinates back to `cfg_acupuncture_points`, and add the new `Point_Group` field.
3. **Staging**: upsert only — for points in the spreadsheet that already exist in staging (matched by doc ID), update `Point_Group` and coordinates; for points in the spreadsheet missing from staging, add them. **No deletions.** This matches the risk mitigation established via a staging/prod comparison: staging was missing 66 points prod has, and still independently referenced `GV14`/`GV4 (TW4)` (3 protocols + 2 treatments + 1 protocol respectively) that were deleted from production — a destructive full-mirror sync would have broken those. Upsert-only avoids that entirely.
4. **Dev** (local emulator, `./emulator-data`, not a persistent cloud project): same upsert procedure as staging.

Scope **RESOLVED**: the `code`/label corrections found this session (`NH5`→`HN5`, `DU20`→`GV20`, `SI18` "Qimai"→"Quanliao") are in scope for the staging/dev sync too, alongside `Point_Group` and coordinates. The sync remains field-scoped, not a whole-document overwrite — `reference_count` and `status` are legitimately environment-specific (e.g. `GV4 (TW4)` was `inactive` in prod but still `active` in staging) and must not be copied from production's values.

### Backup/rollback procedure — RESOLVED ("full protection")

User's chosen procedure, per environment, for both the `cfg_acupuncture_points` corrections and the `treatments` restructuring:

1. **Export a full backup** before making any changes.
2. **Run the changes without deletion** — write the new structure/values, but don't remove the old fields yet (applies most directly to the `treatments` migration, where `stungPointIds`/`stungPointSides` would otherwise be deleted immediately on success per the earlier decision — that immediate deletion is now deferred until after verification).
3. **Manual verification** of the changes.
4. **Run deletions** (removing the old fields) only after verification passes.

This gives a restore-to-start option at any point before step 4. Confirmed this is achievable natively (no custom backup code needed) on all three environments, via two different first-party command families:

| Environment | Backup (export) | Restore (import) |
|---|---|---|
| Production / Staging (real cloud Firestore) | `gcloud firestore export gs://<bucket>/<path>` | `gcloud firestore import gs://<bucket>/<path>` |
| Dev (local emulator, `./emulator-data`) | `firebase emulators:export <path>` | `firebase emulators:start --import=<path>` |

The dev/emulator path is already proven in this codebase — `scripts/auto-save-emulator.js:58-60` already runs `npx firebase emulators:export "<path>" --force --project apitherapyv2` every 5 minutes as an autosave. One mechanical difference to plan around: restoring the emulator requires **restarting the emulator process** with `--import=<path>` (no hot-swap of loaded data while running), whereas `gcloud firestore import` can restore into a live cloud database without downtime.

**Staging/production backups — the daily backup function is verified reliable; a dedicated pre-migration export is used anyway, for timing precision.** There's a deployed Cloud Function `runDailyUnifiedBackup` (`functions/src/index.ts:854-949`, nightly at 3am Israel time, manually-forceable) that exports the whole Firestore database (`collectionIds: []` = all collections) to `gs://<bucket>/ScheduledBackup/<timestamp>/Firestore`. An earlier pass through this plan incorrectly concluded `treatments` wasn't included in it — that was based on the code plus an unverified report, not an actual check. **Directly verified since, two ways**: (1) `gcloud firestore operations list --project=apitherapy-c94a6` shows every recent daily export as `operationState: SUCCESSFUL` with steadily growing document counts (617 on 2026-07-16 → 848 by 2026-08-13); (2) downloaded an actual export's data shards and scanned the raw bytes directly — found genuine `treatments` document records with real schema fields (`patientId`, `createdTimestamp`, `treatmentNumber`, `patientReport`), not just stray text mentions. The daily job works correctly. **Decision**: a dedicated, selective, synchronous `gcloud firestore export` still runs immediately before each migration's real run anyway (see the implementation plan's Phase 3/Phase 5 for the exact commands), scoped to exactly the collection touched, purely for timing precision — the daily job runs once at 3am, so depending on it alone could mean a backup up to ~24h stale relative to when the migration actually runs.
